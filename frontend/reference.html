📋 How this tool works

This tool generates a VBKREQ XML (Vendor Booking Request) for submission to E2open TA and DavisTurner. The UI is split into two independent sections:

📦 Booking — Steps 1 & 2

📊 1 · Upload Supplier Excel
→
📡 2 · Fetch Databricks ASN
→
🗂 3 · Build Master Workbook
→
⚡ 4 · Generate VBKREQ XML
→
🚀 5 · Upload to E2open SFTP

✕ Cancellation — standalone, no re-upload needed

🔍 Enter PO or VB Ref
→
📂 Look up stored booking data
→
⚡ Build cancellation VBKREQ (01 + 177)
→
🚀 Upload to E2open SFTP

Step 1 — Supplier Excel (Supplier PO sheet-DDMMYYYY.xlsx): The supplier fills in the downloadable template — one row per PO in the PO Header sheet. Mandatory (pink) fields: PO_Number, Cargo_Ready_Planned_Collection_Date, Carrier_Booking_Request_Date, Traffic_Mode, Booking_Group, No_of_Cartons, Unit_Weight_KG, Carton_Type. Defaulted (green) fields are pre-set and editable: Traffic_Mode=CFS, Booking_Group=Single Booking, Pack_Type=Bulk Flat, No_of_Cartons=1, Unit_Weight_KG=0.21, Carton_Type=BDCM1. Carton dimensions (Carton_Length/Width/Height/Weight_cm) auto-fill from Carton_Type via a hidden lookup. No PO Lines sheet is required — SKUs and booking quantities are pulled automatically from the Databricks ASN feed for each PO.

Booking_Group controls how POs are consolidated into bookings: Single Booking = one VBKREQ per PO; Multiple POs-BK001…BK025 = all POs sharing the same code are merged into one VBKREQ; Multiple = all POs in the upload combined into a single VBKREQ.

Factory_ID 9999 (Dummy Factory): If a real factory code is not yet known, use 9999. Address validation is skipped for this code — the VBKREQ will be generated without a factory address.

Step 2 — Booking Pipeline (single button): Step 2 is always visible but locked/dimmed until Step 1 completes successfully. Select Purpose Code (13 = New Submission, 15 = Re-Submission) then click ⚡ Build VB & Upload to SFTP. All four stages (Fetch ASN → Build → Generate → Upload) run automatically and results appear in a single table: PO | ASN Ref(s) | VB Ref | VBKREQ File download. A tagged supplier template with prefilled booking refs is also available for download per result row.

Recent Booking History: The collapsible 🕑 panel below Step 2 shows all VBKREQs generated in the last 3 days, loaded automatically after each pipeline run. Click to expand.

📧 Booking Report Email: After each scheduled SharePoint sync (09:00 & 13:00) an HTML summary email is sent to REPORT_TO listing every VBKREQ generated since the last report — Supplier, PO(s), VB Ref, ASN Ref(s), Filename, Booking Group, Cargo Ready Date, Cartons, Weight, SFTP Status. Manual UI bookings are not emailed immediately — they appear in the next scheduled report. On Azure App Service, Always On must be enabled (Basic tier+) or the scheduler will idle and no reports will be sent. The Mail.Send application permission must be granted to the App Registration in addition to Mail.ReadWrite.
📋 Smart Skip — no VBKREQ is raised for:
  • ASNs whose latest notification type in bam036e_asn_v1 is D (deleted/cancelled)
  • POs where Status = C in bam033j_purchase_order_v1
  • ASNs/POs where bookingRequested is already populated (a carrier booking already exists)
Skipped items are shown in the ASN fetch results panel with reason details. They do not block other POs from proceeding.

Cancel Booking (standalone): Enter one or more PO numbers or VB Refs (e.g. 500034236929 or VB-1000000025) in the Cancel Booking card at the bottom. Click Look Up Existing Bookings to verify the records exist in the generation log and confirm ✅ Ready to cancel status. Then click Cancel & Upload to SFTP — the system builds a VBKREQ with PurposeCd=01, reuses the original VB Ref, injects DateTypeCd=177 (cancellation status date), and uploads. No supplier template re-upload is required.

⚠ Legacy bookings: Bookings created before the current version of the tool will show ⚠ No stored data (re-run booking first) in the lookup panel. To enable cancellation for these, re-run the pipeline with the original supplier template once to refresh the stored master row data in the generation log.

📋 Smart Skip — Cancelled & Already-Booked Items

When fetching ASN data from Databricks (Step 2 pipeline), the tool automatically checks three conditions before including an ASN/PO in the VBKREQ build. Items that match any of the following are silently excluded — the remaining active items continue through the pipeline as normal.

ConditionData SourceCheckUI indicator
ASN Cancelled Databricks-bam036e_asn_v1 Latest _notification_type for the ASN is D (deleted/cancelled) 🚫 “ASN {id} cancelled — booking skipped”
PO Cancelled sourcingandbuying.conformed.bam033j_purchase_order_v1 Status = C on the PO record 🚫 “PO cancelled (Status=C) — booking skipped”
Already Booked supplychain.conformed.aim_shipment_detail_v1 bookingRequested field is non-null (a carrier booking request was already sent) 📋 “ASN {id} already has a carrier booking — skipped”
ℹ The bam036e_asn_v1 query is non-fatal — if it fails, the pipeline continues without the cancellation filter and Booking_Qty falls back to aim_shipment_detail orderLineItems.bookedQty → bam033j PODtl.PhysicalQtyOrdered. A warning is logged to the server console. The Already Booked and PO Cancelled checks use data already retrieved by the main ASN/PO queries and have no additional overhead.
✕ Cancel Booking — Standalone Cancellation Flow
StepDetail
1 · Enter inputType one or more PO numbers (e.g. 500034236929) or VB Refs (e.g. VB-1000000025) — comma or newline separated. Both types can be mixed in one lookup.
2 · Look UpFetches matching entries from the generation log (bible/generation-log.json). Displays: Input | PO Number(s) | VB Ref | Booked On. A ✅ Ready to cancel badge confirms stored master row data is present; ⚠ No stored data means the booking predates the current version — re-run the pipeline first to refresh.
3 · Cancel & UploadBuilds a VBKREQ XML with PurposeCd=01, reuses the original Booking_Ref (VB-XXXXX) from the log, injects DateTypeCd=177 (cancellation status date) immediately after the SBK date, and uploads to E2open SFTP. No supplier template re-upload required.
Generation LogEvery successful pipeline run saves the full master row data alongside the VB Ref and timestamp in bible/generation-log.json. This makes cancellation fully self-contained — the Cancel Booking card is independent of the current session state.
📧 Booking Report Email — Scheduled Summary
TopicDetail
TriggerFires automatically at the end of every scheduled SharePoint sync run (09:00 and 13:00, configured via SP_SCHEDULE). Covers all VBKREQs logged since the last report was sent — tracked in bible/report-state.json.
Manual UI bookingsVBKREQs generated manually through the Step 2 pipeline are not emailed immediately. They appear in the next scheduled report (09:00 or 13:00). The generation log is enriched at the time of creation — no data is lost, just batched.
